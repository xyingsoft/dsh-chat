## 46. 错误码目录

错误码属于 `@dsh-chat/contract`，是可判别联合的一部分。用户可见错误码与运维诊断信息分开记录；**用户错误码不得泄露其他组织、成员、文件或群的存在性**。

可重试性是错误码的固有属性，不由调用方猜测：`retryable` 表示同一幂等键重试可能成功，`terminal` 表示重试无意义，`conditional` 表示需先解决前置条件（如重新确认、补拉、扩容）后再试。

| 错误码 | HTTP | 类别 | 可重试性 | 幂等语义 |
|---|---:|---|---|---|
| `UNAUTHENTICATED` | 401 | 认证 | conditional | 重新认证后可重试 |
| `TIME_SKEW` | 401 | 认证 | conditional | 按签名服务器时间修正偏移后重试 |
| `SERVER_IDENTITY_MISMATCH` | 495 | 认证 | terminal | 需管理员确认签名轮换，禁止自动重试 |
| `DEVICE_RESTRICTED` | 403 | 风险 | conditional | 完成风险处置后可重试 |
| `DEVICE_REVOKED` | 403 | 风险 | terminal | 需重新注册设备 |
| `FORBIDDEN` | 403 | 授权 | terminal | 权限变更前重试无意义 |
| `NOT_FOUND_OR_FORBIDDEN` | 404 | 授权 | terminal | 统一返回，不区分存在性 |
| `RECIPIENT_INACTIVE` | 409 | 授权 | terminal | 目标已离开组织 |
| `CONFIRMATION_REQUIRED` | 428 | 确认 | conditional | 需先取得确认挑战 |
| `CONFIRMATION_EXPIRED` | 428 | 确认 | conditional | 必须重新展示摘要并确认 |
| `VERSION_CONFLICT` | 409 | 并发 | conditional | 读取最新版本后以新版本号重试 |
| `SYNC_DIVERGED` | 409 | 一致性 | conditional | 进入对账流程，停止自动重发 |
| `MEMBER_LIMIT_REACHED` | 402 | 配额 | conditional | 需扩容或释放名额 |
| `STORAGE_QUOTA_EXCEEDED` | 402 | 配额 | conditional | 需清理或扩容 |
| `BOT_BUDGET_EXCEEDED` | 402 | 配额 | conditional | 需管理员调整预算 |
| `RECIPIENT_QUEUE_FULL` | 507 | 容量 | conditional | 接收方消费后可重试，发送未被接收 |
| `GROUP_LOG_CAPACITY_EXCEEDED` | 507 | 容量 | conditional | 需保留策略或容量处理 |
| `SANDBOX_QUOTA_EXCEEDED` | 200 | 执行 | terminal | 尝试状态为 `failed`，保留检查点 |
| `RESOURCE_SNAPSHOT_FORBIDDEN` | 403 | 内容策略 | terminal | 目录禁止版本快照 |
| `SHARE_UNAVAILABLE` | 410 | 内容状态 | terminal | 已过期或已撤销 |
| `RESOURCE_GONE` | 410 | 内容状态 | terminal | 已物理清理 |
| `ATTACHMENT_UNAVAILABLE` | 200 | 内容状态 | conditional | 消息仍持久化，附件保留期内重试 |
| `EGRESS_BLOCKED` | 403 | 出站 | terminal | 目标不在 allowlist 或命中私网防护 |
| `PLUGIN_REVOKED` | 403 | 供应链 | terminal | 版本已撤销，能力租约失效 |
| `NOT_IMPLEMENTED` | 501 | 部署 | terminal | 该部署层未装载对应插件 |
| `RATE_LIMITED` | 429 | 限流 | retryable | 含 `retryAfter`，不泄露他人用量 |
| `REVIEW_REQUIRED` | 409 | 评审 | conditional | 项目策略要求评审结论后才能完成 |
| `REVIEW_SUPERSEDED` | 409 | 评审 | conditional | 关联产物已变化，需重新评审 |
| `DEPENDENCY_CYCLE` | 409 | 工作项 | terminal | 依赖关系将形成环 |
| `ARTIFACT_NOT_ACCEPTED` | 409 | 协作 | conditional | 候选产物需有写权限成员确认 |
| `PROTOCOL_VERSION_UNSUPPORTED` | 426 | 协议 | terminal | 需升级 host 或 relay |
| `SERVICE_READ_ONLY` | 503 | 恢复 | retryable | 处于 `read_only_recovery` |

`SANDBOX_QUOTA_EXCEEDED` 与 `ATTACHMENT_UNAVAILABLE` 映射为 200，因为它们是被正常返回的领域状态而不是请求失败；调用方按状态机处理，不按 HTTP 错误处理。

**权限拒绝、schema 无效、配额不足、资源不存在和版本冲突是终态错误，异步任务不得对其自动重试。**

## 47. 术语表

以下术语在 `@dsh-chat/contract` 中有唯一定义，各包实现必须使用同一口径，不得在插件内重新定义同名概念。

| 术语 | 含义 |
|---|---|
| `OrganizationId` / `WorkspaceId` / `ProjectId` | 服务端生成的品牌化不透明 ID，构成三级归属层次 |
| `AccountId` / `DeviceId` | 账号与设备标识；账号可有多设备，设备私钥不上传 |
| `MessageId` | 客户端生成的 UUIDv7，与发送者组成幂等键 |
| `MessageRevision` | 单调递增的消息版本号，编辑追加事件而非覆盖 |
| `DeliverySeq` | relay 为私聊收件人队列项分配的单调序列，按接收人分区 |
| `GroupLog` | 按 `GroupId + membershipRevision` 分区的群消息追加日志 |
| `GroupMessageSeq` | 群日志内单调递增序列，成员各自持游标读取 |
| `ThreadMessageSeq` | 线程内单调序列，仍存储于所属群日志分区 |
| `membershipRevision` | 群成员关系版本，仅表示成员变更，不表示已读 |
| `AccountStateSeq` | 账户级状态变更流序列，用于跨设备已读与偏好同步 |
| `StreamEpoch` / `HighWatermark` | 不可回退的流代次与已公布水位，用于故障恢复对账 |
| `BlobObject` | 内容寻址的物理字节对象，被消息与资源共同引用 |
| `ResourceVersion` | 组织共享存储中的不可变资源版本 |
| `MessageContentGrant` | 绑定消息、接收人范围与保留期的内容读取授权 |
| `GroupHistoryGrant` | 群历史读取授权，含范围上限游标与有效期 |
| `ShareableItem` | 可共享对象的统一抽象，含访问级别与有效期 |
| `CollaborationSession` | 从个人会话显式选择上下文创建的协作单元 |
| `ExecutionProvider` | 在隔离沙箱中运行协作执行尝试的服务 |
| `RepositoryBinding` | 项目与群对仓库的绑定，含访问模式 |
| `CodeChangeRecord` | 经远端验证的提交与项目/工作项/AI 使用的关联记录 |
| `BotServiceAccount` | Bot 的独立身份，权限静态绑定，不随调用者提升 |
| `BotAccessGrant` / `DelegationGrant` | Bot 读取授权与最小范围不可转授委托 |
| `PlanLimits` | 版本化的套餐容量与配额配置 |
| `RetentionPolicy` | 版本化的各类对象保留期、配额与清理规则 |
| `ConfirmationChallenge` | 绑定操作摘要的一次性高风险动作确认 |
| `SecurityRiskEvent` | 设备风险事件，驱动 `restricted` 等管制状态 |
| `RecoveryKit` | 账号恢复材料，含恢复公钥与守护人阈值策略 |
| `AccountTombstone` | 账号注销后用于保留协作事实的不可逆匿名标识 |
| `ReviewId` | 工作项评审关口，`approved` 只对锁定的产物版本生效 |
| `CommentRevision` | 评论修订号，编辑追加而非覆盖 |
| `AuditEvent` | 记录事实与引用、不含内容的审计条目 |
| `ProtocolVersion` | host 与 relay 协商的协议版本 |

## 48. 编码规范

- 使用严格 TypeScript、品牌化不透明标识符、可判别联合类型，并对封闭的消息和命令类型使用 `assertNever`。
- 协议 schema 只放在 `@dsh-chat/contract`；只在 HTTP、数据库、文件系统、队列和浏览器请求这些边界解析。
- 错误码目录、`AuditEvent` 结构、`ProtocolVersion` 与术语表都属于 `@dsh-chat/contract`，插件不得自定义同名概念或私有错误码；新增错误码必须同时声明 HTTP 映射、可重试性与幂等语义。
- host 与 relay 在建立设备会话时协商协议版本，不兼容返回 `PROTOCOL_VERSION_UNSUPPORTED` 并停止组织写入；升级顺序固定为 relay 先升、host 后升，relay 必须能同时服务兼容窗口内的新旧协议。
- 界面文案走 DSH 既有 locale 机制，不在运行时拼接可翻译句子；时间以 UTC 存储与比较，保留期与有效期按服务端时间计算，长度上限按字素簇而非字节计算。
- 所有 Cordis 注册通过 `ctx.effect()` 或 `ctx.on()` 完成，并返回每个 disposer。
- 除 `@dsh-chat/contract` 外，身份、组织、消息、内容、通知、协作、仓库、Bot、分析、审计、host 和 client 均必须是可独立装载的 Cordis 插件；bundle 只负责配置和排序，不实现业务单例。
- 每项跨包能力都要有服务定义、服务提供者和消费者；服务定义不得导入具体 provider，消费者不得导入 relay、数据库或对象存储实现细节。
- 插件声明所需服务、配置 schema、权限、持久事件、启动/停止行为和健康状态；**缺少必需服务时加载失败，卸载时取消任务、关闭连接并释放租约，不能留下路由或事件监听**。
- 每个会改变状态的 relay 或 host 操作都使用参数化查询和明确事务边界。
- 套餐限制、预算阈值、角色比较组、排名权重、文件限制和保留期都是经 schema 校验的组织配置；**实现不得把部署可变值写成代码常量**。
- 心跳阈值、在线可见策略、仓库提供方、webhook 验签算法、允许访问模式和提交归因规则也属于版本化组织策略。
- 缓存键、数据库查询、对象存储路径、队列分区和异步任务都**必须**携带 `OrganizationId` 与权限/资源修订；**失效无法确认时默认拒绝访问**。
- 命令解析器只接受带用户会话、CSRF、设备签名和确认挑战上下文的结构化请求；**禁止从聊天正文、Bot 输出或任何富文本二次解析命令**。
- 插件权限、订阅限制和分析策略的判定由服务端纯函数统一执行，并以策略版本写入审计和分析结果，**确保后续可复算**。
- 所有出站网络重试必须有上限、随机退避、可取消且可观测。**超时必须留下可重试或终态失败，不能留下静默的模糊状态。**
- 浏览器组件只负责呈现。共享视图状态放入已声明的 DSH store；持久聊天状态放入 host 数据库。
- 使用安全 DOM 文本 API 渲染消息内容，并在展示前校验附件元数据。
- 每个状态转换都增加聚焦单元测试；每个发布里程碑增加真实两/三实例集成测试。用户可见的 DSH 集成还需要通过可运行 profile 提供无密钥 replay/snapshot 覆盖。

## 49. 国际化、时区与无障碍

界面文案通过 DSH 的既有 locale 机制提供，插件不自建翻译体系，也不在运行时拼接可翻译句子。首批交付简体中文与英文，缺失文案回退到默认语言并标记，不显示原始 key。

时间在服务端**一律以 UTC 存储与比较**，客户端按用户时区呈现。保留期、有效期、签收期限、聚合窗口和配额窗口的计算使用服务端时间，不受客户端时钟影响；设备时钟偏移只影响请求签名，按 `TIME_SKEW` 处理。**跨时区团队的截止时间必须显示时区标识。**

文本处理按 Unicode 规范：显示名与群名做规范化与同形字检测，防止冒充；文件名净化保留非 ASCII 字符而不是转写丢失；长度上限按字素簇而非字节计算。

无障碍要求所有交互可键盘完成、焦点顺序与视觉顺序一致、状态变化对屏幕阅读器可感知、**颜色不作为唯一状态信号**（投递状态、风险状态、在线状态都必须有文本或图标），并遵循 DSH 主题 token 的对比度约定。**未读计数、投递失败和风险处置这类关键状态必须有非视觉表达。**

## 50. 开放决策

以下问题尚未定论，需要在对应阶段开始前确定。括号内为最晚需要答案的阶段。

> **开放决策必须在对应阶段启动前关闭。** 关闭时应同步更新受影响的需求/架构/细节文档，并在此处标注结论与决策日期。

### 50.1 产品与范围

- P1 前是否需要支持群主转让和群主丢失恢复？（P1）
- 线程、表情回应和转发的定级是否需要调整，特别是线程在 P1 缺席期间群内长讨论的替代方案？（P1）
- 语音消息是否作为文件子类型启用，若启用则录制时长、转码、转写和保留期如何限制？（P2）
- 组织是否需要部门、成本中心和跨工作区经理等更复杂的层级，还是先保持组织/工作区/项目三级？（P3）
- 评审是否允许项目级配置为可选，若可选则如何在跨项目排行中消除“无需评审”带来的口径差异？（P3）
- 工作项跨项目依赖是否在 P1 开放，还是先限制为同项目内依赖？（P1）

### 50.2 安全与合规

- ~~第二验证因素是否在 P0 即对组织所有者强制，`webauthn` 能否提前到 P3？（P0）~~
  **已关闭（2026-08-30）：所有者在 P0 强制 `totp` + 备用码；`webauthn` 不提前，保持 P4。**
  所有者能删组织、改所有人的角色、导出全部审计，而自建组织里所有者往往就是部署者本人 —— 一个被盗的所有者账号等于整个组织。只强制这一个角色不需要 P3 那套按角色分级的策略引擎，一个策略位加一步注册引导就够。
  `webauthn` 不提前是因为它覆盖的是同一个威胁（凭证被盗），但要额外背上平台认证器 API 与浏览器支持矩阵 —— 提前它会占用 P3 的预算却不改变威胁模型。落点见[身份与权限 §8](./01-identity-and-permission.md#8-第二验证因素)。
  *这是一条按默认取值关闭的决策，产品侧若有不同判断可推翻，推翻时同步改上面那一节。*
- 组织所有权接管的公示期长度、守护人阈值和部署管理员介入边界如何按组织类型区分？（P1）
- P1 允许哪些文件类型？对公网 relay 的恶意软件扫描和内容安全承担什么责任？（P1）
- 审计哈希链在 L2 是每日锚点还是逐条链接，外部归档由谁托管与验证？（P2）
- 账号注销宽限期与组织删除宽限期是否允许按组织或合同调整，法律保留如何覆盖匿名化流程？（P3）
- P4 是否允许端到端恢复密钥托管，还是仅允许用户离线恢复包和守护人阈值恢复？（P4）
- 端到端加密模式下设备侧本地索引的存储上限、跨设备差异提示和“不做本地索引”选项如何取舍？（P4）
- 端到端加密群的成员规模上限是多少，500 人群的成员密钥管理协议开销、epoch 轮换频率与离线成员补齐策略如何权衡？（P4）
- 数据驻留是否按区域强制，多区域部署下组织分片、备份、审计归档和出口代理各自的落地区域如何约定？（P4）

### 50.3 集成与运维

- 公共群 Bot 由 relay 运维者、群主还是独立可信服务账号托管？（P2）
- 首批支持哪些代码仓库提供方，如何处理自建 Git 服务、镜像仓库、作者邮箱映射和强制推送？（P1）
- 企业目录同步、单点登录和私有化部署采用哪些身份提供者与审计导出格式？（P4）
- ~~在线/空闲/离线阈值是多少，组织是否允许按项目订阅成员状态变化？（P0）~~
  **已关闭（2026-08-30）：心跳 30 秒，`online` ≤ 90 秒，`idle` ≤ 10 分钟，超出即 `offline`；按项目订阅不在 P0 做。**
  90 秒是三个心跳周期 —— 设一个周期的话，一次 GC 停顿或网络抖动就会让人「闪断」。10 分钟覆盖开会、倒水这类离开，短于 5 分钟会让刚看过消息的人显示为闲置。
  按项目订阅不做：它会让在线状态的扇出与授权判定都按项目切一遍，而 P0 的组织规模用不上这个粒度。可见性仍按 §9.1 的三档（全员/项目成员/隐藏）—— 那是**谁能看**，不是**订阅谁**，两件事不要混。落点见[身份与权限 §9.1](./01-identity-and-permission.md#91-在线状态)。
  *这是一条按默认取值关闭的决策，运营数据出来后可以调 —— 阈值本身属版本化组织策略，改它不需要改协议。*
- 哪些通知可由组织标记为紧急，以及这种通知如何避免被滥用？（P1）
- 限流基线表中的默认值是否需要按组织类型分档，自建组织能否自行放宽消息与搜索速率？（P1）
- 各部署层的 SLA、RTO 与 RPO 数量级如何写入合同，RPO 与已公布高水位的间隔如何对齐？（P3）
- 数据导入与跨平台迁移支持哪些来源，作者映射与历史授权如何重建，导入内容如何在审计与排行中标记？（P3）
- L1 SQLite 到 L2 PostgreSQL 是否支持原地升级，还是只支持导出/导入？该问题影响自建组织的升级承诺，需在 P1 前明确。（P1）

### 50.4 商业化

- 团队版与企业版各自的默认人数、存储、Bot、模型预算和支持范围如何定价，哪些能力允许自建组织使用？（P3）
