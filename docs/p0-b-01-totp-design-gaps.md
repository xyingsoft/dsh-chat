# P0-b-01：TOTP 契约与后端基础——设计缺口

> 状态：🔶 规格审计完成；纯函数验证子工单已完成，业务契约仍等待冻结。
> 日期：2026-09-07
> 本文不新增运行时语义；只记录现有文档已经明确的约束，以及实现前必须补齐的契约字段。

## 已经明确的约束

来源：`docs/archive/03-details/01-identity-and-permission.md` §8、`docs/README.md` §8.1、`docs/ui-design.md` §3.1。

- P0 对组织所有者强制启用 `totp` 与一次性备用码；`webauthn` 不提前到 P0。
- TOTP 遵循 RFC 6238，30 秒时间步，容忍前后各一个时间步。
- TOTP 已消费时间步必须记录并拒绝重放。
- 第二因素验证失败按账号和设备分别限流，并可能提升风险评分。
- 错误信息不得区分“因素不存在”和“因素错误”。
- 登记、替换、删除第二因素属于高风险动作，需要 `ConfirmationChallenge` 与已授权设备确认。
- 删除最后一个 active 因素时，强制策略生效则必须拒绝。
- 启用第二因素时一次性签发备用码，只展示一次，只保存哈希；备用码不能替代设备签名。
- 所有状态改变需要参数化查询、明确事务边界、审计同事务。

## 当前仍缺少的实现契约

这些内容不能通过代码猜测，必须在契约层或安全细节文档中冻结：

1. **TOTP 参数**：HOTP hash 算法（SHA-1/SHA-256/SHA-512）、输出位数、密钥字节长度、`otpauth://` issuer/account 格式。
2. **密钥保护**：TOTP secret 在 relay/host 的存储位置、加密/封装方式、密钥轮换与擦除语义。明文 secret 不应进入审计或普通 API 响应。
3. **登记流程**：challenge 的字段、有效期、绑定的设备/账号/操作摘要、登记成功前是否允许重试，以及并发登记如何处理。
4. **验证流程**：验证码验证请求字段、服务端时间源、前后时间步去重键、同一时间步多个设备是否分别允许一次成功。
5. **撤销/替换流程**：当前因素状态枚举、active/revoked 的转换边界、替换是否要求先验证旧因素、最后因素删除与组织强制策略的原子判定。
6. **错误契约**：新增错误码、HTTP 映射、是否可重试、幂等语义、客户端可见文案；尤其需要区分安全上不可区分的认证失败与结构性错误。
7. **审计契约**：登记/验证成功与失败、重放、限流、撤销、替换各自的事件类型和目标引用，且不得写入 TOTP secret 或验证码。
8. **迁移契约**：现有 schema 中是否已有因素表/字段；若没有，表名、字段、唯一约束、索引、加密元数据和迁移编号。
9. **测试基线**：固定服务端时间注入方式、时钟步边界、重放窗口、并发请求、跨设备、组织者强制门禁和限流计数的验收样例。
