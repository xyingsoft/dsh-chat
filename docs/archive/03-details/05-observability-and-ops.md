## 40. 可观测性、SLO 与容量目标

relay 是权威运行面，因此可观测性属于交付范围而不是运维自选项。指标、日志与追踪都以 `OrganizationId` 打标，但跨组织仪表盘只读取聚合结果。

必须暴露的指标面至少包括：私聊队列深度与最老未 ACK 年龄、群日志写入速率与成员游标滞后、outbox 待处理量与 `dead_letter` 计数、租约持有与过期回收量、长连接活跃数与 `draining` 比例、索引滞后、异步任务各状态分布、分片健康与主从延迟、`StreamEpoch` 与 `HighWatermark` 推进情况、限流命中率、认证失败与风险事件速率、存储与配额水位、模型调用成本与预算消耗。

日志规范集中如下：结构化输出，携带请求 ID、调用链 ID、`OrganizationId`、操作 ID 与错误码；消息正文、附件字节、提示词、模型输出、token、密钥、webhook secret、完整 IP 与恢复材料一律不写入日志；查询词、文件名与仓库 URL 按组织策略脱敏。运维诊断日志与用户可见错误码分离存储。

### 40.1 服务等级目标

服务等级目标按部署层给出数量级，作为验收与容量规划基线而非合同承诺：

| 指标 | L1 单节点 | L2 团队版 | L3 企业版 |
|---|---|---|---|
| 支撑账号数 | 32（默认上限，可由部署管理员调整） | 数千 | 按分片线性扩展 |
| 活跃群数量级 | 百 | 万 | 十万 |
| 私聊投递端到端 p95（双方在线） | < 2 s | < 1 s | < 1 s |
| 群消息可见 p95 | < 3 s | < 1.5 s | < 1.5 s |
| 通知收件箱写入 p95 | < 2 s | < 1 s | < 1 s |
| 同步游标滞后 p95 | < 5 s | < 3 s | < 3 s |
| 单群成员上限 | 不超过该部署的账号上限 | 500 | 按合同与区域部署确定 |
| 可用性目标 | 无 | 99.5% | 99.9% 起，按合同 |
| RPO | 最近一次备份 | ≤ 5 min | ≤ 1 min |
| RTO | 人工恢复 | ≤ 4 h | ≤ 1 h |

RPO 与“已公布高水位”直接相关：**任何声明的 RPO 都不得小于恢复副本能证明包含的高水位间隔，否则必须进入 `read_only_recovery` 而不是按 RPO 宣称无损。**

表中的容量数字是数量级基线，实际强制值仍由版本化的 `PlanLimits` 配置决定；**两者冲突时以 `PlanLimits` 为准，本表不得被实现读作代码常量。**

P0 验收即需记录上述基线的实测值；**达不到数量级时必须在文档中修正目标，不允许以“后续优化”留空**。

## 41. 协议版本协商与升级顺序

host 与 relay 独立升级，因此协议兼容性必须显式协商而不是靠同步发版。

`@dsh-chat/contract` 声明 `ProtocolVersion`（单调递增整数）、最低支持版本和各事件的 `eventFormatVersion`。host 在建立设备会话时提交自身协议版本与已支持事件格式集合；relay 返回协商结果、服务端当前版本、最低支持版本和弃用截止时间。

协商失败返回 `PROTOCOL_VERSION_UNSUPPORTED`，**host 显示明确的升级提示并停止组织写入，不进入静默降级或部分可用状态**。

兼容窗口默认为两个次要版本或 90 天中的较长者。窗口内 relay **必须**同时接受旧版本命令并以旧事件格式向旧 host 投递；窗口结束前向管理员与受影响成员发出通知。

**升级顺序固定为 relay 先升、host 后升**：relay 必须先具备同时服务新旧协议的能力，再允许 host 升级。**新版本 relay 不得要求所有 host 已升级才能启动。** 数据库迁移遵循扩展、双读/双写、回填校验、切换读取、收缩五步，且收缩步骤只能在所有部署内 host 版本与备份恢复窗口都越过兼容期后执行。

部署管理台或 CLI 至少提供：版本与协商状态查询、迁移进度与暂停、分片与水位健康、outbox 与 `dead_letter` 处置、黑名单与限流调整、备份与恢复演练触发、密钥轮换、组织挂起与保留策略调整。**管理台操作全部走同一套认证、确认挑战与审计路径，不设置绕过授权链的后门接口。**

> 迁移五步的详细定义，见[消息投递与持久化 §29.1 迁移策略](./02-delivery-and-persistence.md#291-迁移策略)。
