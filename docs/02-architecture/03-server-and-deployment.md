# 五、服务端运行面（上）：结构与部署分层

本篇定义 relay 的内部结构、部署演进与数据持久化。核心原则是单事务加 outbox、按组织分片、不静默丢数据。

> **本文档属于架构层**。它定义服务端的组件切分与写入协议骨架；具体的投递流程、持久化字段与限流数值在[细节层](../03-details/02-delivery-and-persistence.md)展开。

**关键约束**（最易被违反的三条，不能替代正文）：

1. 每个业务记录都带不可变 `OrganizationId`，请求令牌、设备签名、路径目标与数据库行的组织 ID 必须一致。
2. 领域对象与 outbox 必须在同一数据库事务中写入；异步投递结果不能反向决定原事务是否成功。
3. 后一层只替换服务提供者，不复制或分叉领域规则；各层执行同一套认证、授权、幂等、审计、保留与恢复语义。

## 26. 服务端闭环与写入协议

relay 是**多租户的组织协作服务，不是单个内存转发脚本**。每个业务记录都带不可变 `OrganizationId`，**请求的 token、设备签名、路径目标和数据库行的组织 ID 必须一致**。

服务端由边缘接入层、无状态 API 层、持久化业务层、异步任务层和对象存储层组成。P0 可以在单节点上部署这些逻辑组件；团队版和企业版按组织 ID 分片，但不改变协议和权限语义。

```text
边缘接入层           TLS 终止、证书固定支持、DDoS/WAF、请求上限、IP 风险初筛
认证与设备服务       账号、密码验证、设备公钥/指纹、令牌、签名证明、邀请码和恢复
会话与状态服务       浏览器会话、设备会话、长连接租约、心跳、在线聚合和风险管制
组织与策略服务       组织 ID、套餐、成员、角色、ACL、项目、确认挑战、配额和预算判定
消息与投递服务       私聊队列、群日志、成员游标、租约、ACK、去重和 E2E 信封路由
内容服务             附件预约、对象存储、资源版本、下载授权、加密、缓存和清理
仓库集成服务         仓库绑定、凭证保管、webhook 验签、提交验证和更新事件
协作服务             工作项、共享对象、协作会话、执行租约和会话隔离
通知服务             收件箱、偏好、outbox、在线推送、长连接和补拉
Bot 调度服务         Bot 策略校验、调用队列、隔离会话、Bot host 路由和结果回写
插件目录服务         提交、审核、签名验证、发布、启用、升级、撤销和能力控制
分析服务             用量归集、成本预算、报告草稿、比较组和排行计算
审计与运维服务       审计事件、黑名单、限流、分片、备份、恢复、指标和密钥轮换
```

### 26.1 写入协议

一个会改变业务状态的 HTTP 命令**必须**遵循“认证、授权、版本检查、同一数据库事务写入领域对象和 outbox、提交后异步投递”的顺序。

**请求在事务提交前失败时返回错误且不产生任何可见领域状态**；事务提交后网络连接断开时，调用方用**同一幂等键**查询最终结果。

outbox 任务可以重复执行，因此消费方以事件 ID 去重；**通知、SSE 推送、Bot 调度和媒体清理不能反向决定原事务是否成功**。

所有异步任务具有 `queued`、`running`、`retrying`、`succeeded`、`failed`、`cancelled` 或 `dead_letter` 状态，含尝试次数、下次重试时间、最后错误和关联领域对象。

可重试错误包括网络短暂失败、可恢复数据库锁冲突和 Bot host 暂时不可用；**权限拒绝、schema 无效、配额不足、资源不存在和版本冲突是终态错误，不能自动重试**。

Bot host 处理完成后只能提交一个带调用 ID 的结果命令。relay 检查调用仍有效、Bot 仍是项目成员、输出仍符合大小和策略限制后，才把结果写成群消息或共享产物。

relay 重启时从数据库恢复未 ACK 队列、未完成上传、未完成 outbox、未完成 Bot 调用和租约；过期租约会被安全释放或重投，而不会把 `running` 永久卡住。

服务端需要分别记录用户可见错误码和运维诊断。**用户错误码不得泄露其他组织、成员、文件或群的存在性。**

## 27. L0 至 L3 渐进部署

系统按共享协议与可替换服务实现分层演进；后一层替换已定义的服务提供者，不复制或分叉领域规则。任何层都必须执行同一套认证、授权、幂等、审计、保留与恢复语义。

| 层级 | 交付包 | 运行与依赖 | 覆盖范围 |
|---|---|---|---|
| L0 契约层 | `@dsh-chat/contract` | 纯 TypeScript；零运行时依赖 | 品牌化 ID、命令、事件、错误码、状态机、schema 输入/输出与服务接口；无副作用，浏览器和 Node 均可引用 |
| L1 社区 bundle | `@dsh-chat/kernel` | 单 Node 进程 + SQLite | 装载身份、组织、消息、通知与审计等基础插件，形成单组织文本协作；附件、邮件、外部 webhook、Bot 执行和高可用接口明确返回 `NOT_IMPLEMENTED` |
| L2 团队 bundle | `@dsh-chat/team` | 无状态 API 实例 + PostgreSQL + Redis + 对象存储 + SMTP | 以配置层替换存储、nonce、通知和内容提供者，并加入附件、邮件、基础限流、备份和恢复插件 |
| L3 企业 bundle | `@dsh-chat/enterprise` | 分片 API 集群 + PostgreSQL 分区/副本 + 对象存储 + KMS/HSM + 专用安全服务 | 在不改动领域消费者的前提下替换或增挂 KMS、隔离执行、受控出站、审计归档和目录同步插件 |

`@dsh-chat/contract` 只定义类型和接口，不携带数据库驱动、HTTP 框架或业务副作用，压缩产物目标小于 100 KB。`kernel`、`team` 和 `enterprise` 都是 bundle，不承载业务单例；它们只排列插件、提供默认配置并选择提供者。**L1 的 SQLite schema 从第一版起包含 `OrganizationId`、事件 ID、操作 ID、策略修订、账户同步序列、加密元数据和恢复水位字段**，避免把后续多租户、E2E 或恢复需求变成破坏性表结构重写。

L2 通过服务注册替换 L1 的 SQLite 存储、内存 nonce、同步通知和本地附件实现，例如替换为 PostgreSQL 存储、带 TTL 的 Redis nonce、事务 outbox 和对象存储；领域命令、错误码与权限判定不因部署层改变。L3 的 KMS、沙箱、审计和出口代理由 API/worker 通过受认证的内部服务接口显式调用，不采用可被应用代码绕过的“劫持所有 fetch”或通用 gRPC 拦截器。

> 各部署层对应的迭代阶段，见[迭代计划 P0–P4](../04-roadmap/03-iteration-plan.md)。
> 各部署层的容量与 SLO 目标，见[可观测性与运维 §40.1 服务等级目标](../03-details/05-observability-and-ops.md#401-服务等级目标)。
> 各部署层的审计不可变形态，见[安全与合规 §37 审计事件模型](../03-details/04-security-compliance.md#37-审计事件模型)。
