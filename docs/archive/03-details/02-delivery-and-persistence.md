## 28. 可靠投递流程

可靠性语义是：**从 relay 接收消息开始，到接收方把消息写入持久化存储为止，至少投递一次**。

1. 浏览器把消息提交给 host。
2. host 校验输入，在一个本地事务中写入 `status = pending` 的发送记录，然后向 relay 发送。
3. relay 认证设备并授权目标。私聊在一个事务中提交已接收消息和目标收件人队列项；群聊在一个事务中提交消息、当前成员版本快照和单条 `GroupLog` 记录，不为每位成员同步插入队列项。
4. 发送方 host 把记录改为 `accepted`；它不能声称消息已送达或已读。
5. 私聊接收方 host 拉取一个带租约的批次，在一个本地事务中写入此前未见的消息和已接收投递记录，然后 ACK 这些 `DeliverySeq`；群成员按自己的 `GroupMessageSeq` 游标补拉有权读取的 `GroupLog` 记录并持久化游标。
6. 如果接收方在 ACK 前崩溃，租约到期后 relay 重投。同一投递的本地接收记录让再次写入幂等，host 随后 ACK。

私聊目标队列容量不足时，relay **必须在接收新消息前**以 `RECIPIENT_QUEUE_FULL` 拒绝发送。群消息由群日志配额约束；配额耗尽时返回 `GROUP_LOG_CAPACITY_EXCEEDED`，并由管理员通过保留策略或容量扩展处理。

**relay 不得淘汰已经接收但尚未 ACK 的私聊消息，也不得跳过尚在保留期内的群日志序列，为后续流量腾出空间。**

relay 按已公布的保留期保存未 ACK 消息；**管理员删除队列或保留期到期时，系统必须让发送方看见终态失败**。

每个设备同时只允许一个有效的租约拉取批次，而不是每个账号一个批次，从而为未来的多设备支持保留清晰的所有权。

### 28.1 流代次与分叉检测

relay 为每个私聊队列分区和群日志分区维护**不可回退**的 `StreamEpoch` 与 `HighWatermark`，host 在同步请求、ACK 和账户阅读水位中同时携带两者。数据库恢复、主从切换或分片故障转移**若不能证明恢复副本至少包含已公布的高水位，就不能直接恢复为可写**；服务进入 `read_only_recovery`，从持续日志补齐，或提升 epoch 并要求 host 从已签名检查点重新对账。

host 发现服务端 epoch 变化、服务端高水位低于本地已确认水位、或同一序列的消息摘要不一致时，进入 `sync_diverged`，停止 ACK、自动重发和新的组织写入，只上报本地已确认操作 ID 与检查点供 relay 对账。对账结果只能是补回缺失事件、明确标记尚未提交的本地发送失败，或由用户确认恢复副本；**不得静默把 `seq 100` 当作从未发生**。

> RPO 与已公布高水位的对齐要求，见[可观测性与运维 §40.1](./05-observability-and-ops.md#401-服务等级目标)。

## 29. 本地与 relay 持久化

P0 的 host 和 relay **都必须使用事务型数据库**；反复重写的 `state.json` 不足以保证消息队列、去重和附件元数据的一致性。

host 数据库存储账号/设备引用、加密恢复包引用、登录方式引用、固定 relay 指纹、组织切换状态、在线可见性偏好、风险受控状态、联系人、群快照、群日志游标、历史授权、仓库链接缓存、消息、接收投递记录、发送状态、附件/资源授权元数据、个人用量摘要和同步游标。

凭证、设备私钥、E2E 密钥包和 relay 指纹**优先存放在操作系统提供的受保护存储**；不具备该能力时，以用户提供的秘密加密后落盘，**且绝不通过浏览器 API 返回**。设备进入 `restricted` 时立即清除该组织的会话 token、解密材料和敏感缓存。

附件字节存放在受访问控制的数据库外目录；附件元数据和“写入完成”标记与让消息可见的状态处于同一事务中。

relay 数据库存储账号、密码验证值、公钥/指纹、第二验证因素与备用码哈希、恢复公钥与守护人策略、设备状态、token 撤销记录、nonce、风险事件、IP/粗粒度区域历史、在线可见范围、组织成员关系、策略修订、确认挑战、黑名单、仓库绑定与 webhook 验证配置、代码更新记录、工作项与依赖关系、评审记录、评论与修订、候选产物、联系人请求、有向拉黑记录、群事件、群日志、线程序列、表情回应、成员游标、已读水位、`StreamEpoch`、`HighWatermark`、已签名同步检查点、历史授权、已接收私聊消息、队列项、租约、ACK 记录、附件预约、`BlobObject`、`MessageContentGrant`、资源版本、保留策略、缓存失效事件、搜索索引条目、`AuditEvent` 与哈希链锚点、导出与注销请求状态和异步任务状态。

### 29.1 迁移策略

数据库 schema 版本单调递增，迁移必须使用真实历史数据库测试。迁移分为扩展、双读/双写、回填校验、切换读取、收缩五步：先增加可空字段/新表/新索引和版本化 API，再由新旧代码同时写入，后台分批回填并校验计数、摘要和外键，灰度切换读取端，最后仅在所有部署版本与备份恢复窗口越过兼容期后删除旧字段。

**禁止把生产升级设计为长时间锁表的整表 `ALTER TABLE`。** 大表新增索引使用在线/并发能力或影子表切换；迁移任务有批次上限、进度游标、可暂停、可重试和回滚读路径。**P0 即保存 `encryption_meta`、事件格式版本、设备/账户同步状态和可选扩展表**，而不是在 P4 到来时重写消息主表；**预留字段不是未定义 JSON 垃圾桶，字段语义、所有者和解析版本必须在 L0 协议中明确**。

备份必须加密并演练恢复；保留和删除规则必须区分本地历史、relay 投递数据、媒体、审计元数据、风险记录、密钥包、缓存和运行日志。**KMS/HSM 密钥、数据密钥和设备私钥不写入同一备份明文。**

> 迁移与协议升级的顺序约束，见[可观测性与运维 §41 协议版本协商与升级顺序](./05-observability-and-ops.md#41-协议版本协商与升级顺序)。
> 迁移测试要求，见[测试与验收策略](../04-roadmap/04-test-strategy.md)。
