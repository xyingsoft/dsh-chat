# dsh-chat 设计文档（AI 迭代版）

> 面向自建团队、受管团队与企业组织的 **DSH Web 协作平台**。
> 本文件是**唯一实现依据**：定义边界、架构、关键机制、迭代路线与工作流。AI 运行迭代时以此为准。
> 详细规格（完整字段、错误码、验收细节）归档在 [`archive/`](./archive/)，作参考用，不作为独立实现依据。

---

## 1. 这是什么

dsh-chat 是一组 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)（DSH）插件，在 DSH Web 上提供组织化团队协作：

- **身份与设备**、**组织与权限**、**文本私聊**、**工作项与评审**、**通知收件箱**、**审计**。
- 后续演进到群聊、资源库、协作会话、Bot、分析、E2EE 与分片。

**不是**微信集成、微信替代品或账号桥接。聊天记录与私人 AI 会话严格分开；内容只有经用户明确授权才进入 AI 请求。

**核心价值**：让人、项目资源和 DSH AI 工作流处于同一受控组织中。

## 3. 不可违背的设计原则

> 以下原则是评审与验收的硬约束，违反即为缺陷。实现不得以「代码方便」为由突破。

### 3.1 八条边界声明

| 边界 | 含义 |
|---|---|
| **撤回 ≠ 抹除** | 不承诺擦除已截图、导出、复制、缓存或已授权下载的内容 |
| **撤销共享 ≠ 删除** | 只阻止后续读取，不删除已下载的本地副本 |
| **注销 ≠ 抹除他人副本** | 匿名化保留他人已合法接收的协作事实 |
| **执行成功 ≠ 产物被接受** | 候选产物需有写权限成员显式确认 |
| **通知已读 ≠ 任务已知晓** | 签收状态独立于通知状态 |
| **在线状态 ≠ 可打扰** | 只表达 host 存活，不推断阅读或输入 |
| **服务端加密 ≠ 端到端加密** | P0–P3 relay 可读明文；P4 才引入 E2EE |
| **应用层删除 ≠ 约束基础设施管理员** | 自建部署的运维者可直接操作底层存储 |

### 3.2 核心架构约束

- **文档先行**：任何需求/架构变更必须先更新本文档与对应归档规格，再写代码。
- **凭证按层隔离**：浏览器不持组织秘密与设备私钥；host 是浏览器访问组织的唯一入口；relay 不保存设备私钥。
- **没有特权聊天内核**：除 `@dsh-chat/contract` 外一切能力都是可独立装载/卸载的 Cordis 插件。
- **强约束词**：「必须」「不得」「绝不」为硬约束，改为「建议」属需求变更，需走评审。
- **约束自上而下**：需求 → 架构 → 细节 → 排期，下层不得引入上层未声明的需求。

## 4. 总体架构

### 4.1 三层架构

```text
DSH Web 客户端   → 仅呈现与交互，不持组织秘密/relay 凭证/设备私钥
DSH host 插件    → 本地 SQLite 缓存、设备凭证、relay 客户端、同源 /api/chat 与 /api/organization
relay            → 组织权威数据与策略判定，多租户服务端（身份/组织/消息/资源/通知/审计…）
```

- 浏览器通过 host 的同源 API 与事件流访问一切；**浏览器不得直接携带 relay access token**。
- host 是唯一入口，拥有完整请求生命周期与浏览器事件流。
- 客户端不重算权限；界面可用操作来自 host 返回的能力描述，服务端对每次调用完整鉴权。

### 4.2 插件化架构

- 每个能力由三角色组成：**服务定义**（稳定接口/配置/错误语义）、**服务提供者**（SQLite/PG/Redis/对象存储/KMS…）、**消费者**（通过接口调用，不导入提供者数据模型）。
- 插件间持久协作用领域事件 + 事务 outbox，**不用跨插件共享可变内存**。
- 启动顺序由 `inject` 依赖推导：先身份/组织/审计，再消息/内容等消费者；**缺少必需提供者时加载失败，不允许静默降级**；可选能力必须显式 `NOT_IMPLEMENTED`。
- 核心能力矩阵：身份、组织、在线状态、消息、内容、通知、协作执行、工作项、仓库、Bot/插件目录、分析计费、搜索、审计、合规。

### 4.3 服务端写入协议

一个改变业务状态的 HTTP 命令**必须**按序执行：

```
认证 → 授权 → 版本检查 → 同一数据库事务写入领域对象 + outbox → 提交后异步投递
```

- 事务提交前失败：返回错误，**不产生任何可见领域状态**；提交后断网：调用方用同一幂等键查询最终结果。
- outbox 任务可重复执行，消费方按事件 ID 去重；异步投递**不能反向决定原事务是否成功**。
- 可重试错误（网络/锁冲突/Bot 不可用）vs 终态错误（权限拒绝/schema 无效/配额不足/版本冲突——**不自动重试**）。
- relay 重启后从数据库恢复未 ACK 队列、未完成上传/outbox/Bot 调用/租约。

## 5. 关键机制摘要

| 机制 | 要点 |
|---|---|
| **可靠投递** | 至少一次投递 + ACK 幂等；消息与队列项同事务；`DeliverySeq` 单调；队列满在写入前拒绝，不淘汰未 ACK |
| **编辑/撤回** | 追加事件而非覆盖；撤回占一个 revision；幂等；「撤回」与「迟到编辑」按同一尺度比较 |
| **授权** | 组织/工作区/项目三层 + 双层授权判定；10 角色能力表；`organization_id` 显式过滤 |
| **审计** | 仅追加、与领域写入**同事务**；被拒绝的尝试同样留痕；审计表**不含消息正文** |
| **限流** | 多维度配额，按最严格者生效；配置化实现，不写死常量 |
| **错误码** | 用户错误码不得泄露其他组织/成员/文件/群的存在性（如 `NOT_FOUND_OR_FORBIDDEN`） |
| **协议协商** | 版本不兼容返回 `PROTOCOL_VERSION_UNSUPPORTED` 并停止写入，**不静默降级** |

## 6. 部署分层 L0–L3

| 层 | 交付包 | 运行与依赖 | 覆盖 |
|---|---|---|---|
| **L0 契约层** | `@dsh-chat/contract` | 纯 TS，零运行时依赖 | 品牌化 ID、命令、事件、错误码、状态机、schema、SPI |
| **L1 社区** | `@dsh-chat/kernel` | 单 Node 进程 + SQLite | 身份/组织/消息/通知/审计等基础插件，单组织文本协作 |
| **L2 团队** | `@dsh-chat/team` | API + PostgreSQL + Redis + 对象存储 + SMTP | 群聊、附件、资源库、仓库、服务端搜索 |
| **L3 企业** | `@dsh-chat/enterprise` | 分片集群 + KMS/HSM + 安全服务 | 分片、E2EE、审计归档、目录同步 |

- 后一层**替换已定义的服务提供者，不复制或分叉领域规则**；命令、错误码、权限语义不因部署层改变。
- L1 的 SQLite schema **从第一版起**包含 `OrganizationId`、事件/操作 ID、策略修订、账户同步序列、加密元数据、恢复水位字段，避免后续需求变成破坏性表重写。

## 7. 工程结构

```text
dsh-chat/
  packages/chat/
    contract/        纯类型/命令/事件/错误码/schema/SPI
    kernel/          L1 bundle：排列插件 + 默认配置（DSH 安装入口）
    team/            L2 provider 覆盖
    enterprise/      L3 provider 覆盖
    host/            host 插件：本地库、relay 客户端、同源路由、事件发布
    client/          client 插件：DSH slot、页面、store、CSS Modules
    identity/ organization/ workitem/ presence/
    messaging/ content/ notification/ collaboration/
    repository/ bot/ search/ analytics/ compliance/ audit/
  examples/two-users/  两个 host + 一个组织 + 一个项目 + 一个 relay
  vendor/dsh-runtime/  vendored 运行时 tarball（带外锚点校验）
```

- 技术栈：TypeScript（ESM-only）、`@deepseek-ai/cordis` 4.0.1、DSH 运行时 `0.1.2-alpha.1`（对应 DSH Desktop v2.0.4）、React 18 + CSS Modules、SQLite（P0）/ PostgreSQL（P1+）、Node `^22 || >=24`。
- 版本锚定：DSH 运行时依赖**必须精确版本**，不得用 `*`/`latest`/范围匹配；npm 上的 `latest` 指向远早于当前的版本。
- 客户端与服务端同仓；`contract` 是唯一共享协议包。

## 8. 迭代路线图

### 8.1 当前关口：P0-b（下一步）

P0 分 `P0-a` / `P0-b` 两关口，**顺序不可颠倒**。P0-a 全绿，现进入 P0-b，补齐骨架剩余 5 步：

1. **第二因素**：TOTP 登记与校验、备用码、已消费时间步防重放。
2. **组织强制策略**：未登记第二因素前只能访问账号安全设置。
3. **恢复**：`RecoveryKit` 生成、守护人阈值拆分、`recovery_pending` 状态、冻结旧设备、安全通知。
4. **在线可见范围**：在线/空闲/离线阈值、可见范围设置、状态过期与订阅变化通知。
5. **本地搜索**：host 本地索引、索引条目状态机、撤回消息不在索引中残留。
6. **协议验收**：版本协商端到端验收；凭证重放与时间偏移滥用的验收。

> **不得为压缩 P0-a 而删除 schema 字段**：`RecoveryKit`、`ProtocolVersion`、账户/设备同步状态、`encryption_meta` 已在 P0-a 写入协议与数据库，P0-b 只是补验收路径。

### 8.2 后续阶段

| 阶段 | 核心交付 | 验收要点（摘） |
|---|---|---|
| **P1** | 群聊、历史授权、资源库、附件、仓库绑定、服务端搜索 | 三台 host；离线投递期间成员变更、群事件缺口恢复、ACL 逐条复检、撤回不残留索引 |
| **P2** | 协作会话、沙箱执行、候选产物、群 Bot、线程/转发 | 协作会话不包含未选择上下文；沙箱隔离；Bot 不触发二次命令解析；`VERSION_CONFLICT` |
| **P3** | 团队版限制、插件目录、成本大屏、排行、治理 | 超额在提交前拒绝；撤销即终止；仪表盘不读私聊；唯一所有者注销需先转让 |
| **P4** | 分片、E2EE、KMS、审计哈希链、目录同步 | 分片故障转移、密钥轮换、epoch 隔离、哈希链断裂检测、E2EE 下入口按矩阵降级 |

> 每阶段「验收必须覆盖」段落是**准出条件**，不是建议清单。完整验收细节见归档的[迭代计划](./archive/04-roadmap/03-iteration-plan.md)。

## 9. AI 迭代工作流

> 本项目的强制开发流程：**文档先行 + 验收驱动 + 垂直切片**。每个迭代按以下循环执行。

### 9.1 迭代循环

```
1. 选工单   → 从 TODO.md / feature-inventory 取下一个最高优先级未完成项（P0-b 优先）
2. 对齐规格 → 对照本文档 + 归档详细规格，确认验收标准（边界、错误码、状态机）
3. 先写文档 → 涉及需求/架构变更时，先更新本文档与归档规格，再写代码
4. 实现切片 → 垂直切片（端到端可验证），不水平分层堆代码
5. 补测试   → 单元 + 集成 + 拒绝用例（安全路径必测拒绝行为，不只测「未崩溃」）
6. 验收    → 对照该阶段准出条件逐条核对；未达标不得宣布完成
7. 回写    → 更新 TODO.md / feature-inventory 实现状态，记录到 archive/_meta/implementation-log.md
```

### 9.2 每个迭代的检查清单

- [ ] 变更是否从最上层受影响的文档开始？（需求 → 架构 → 细节 → 排期）
- [ ] 是否触达授权/内容授权/出站/执行路径？是则**必须**补拒绝用例 + 安全回归条目
- [ ] 新增状态、错误码、术语是否已登记到归档[契约附录](./archive/03-details/06-contracts-and-conventions.md)？
- [ ] 是否新增/修改了用户可见能力？是则需更新本文档 §8 阶段范围
- [ ] 强约束词是否被无声弱化？（把「必须」改成「建议」= 需求变更）
- [ ] 实现中发现文档有误 → **暂停实现、修正文档、评审合入后再继续**，不得留 `// TODO: 文档待更新`

### 9.3 测试分层（五层）

| 层 | 覆盖 | 要求 |
|---|---|---|
| 单元 | 状态机、权限纯函数、schema、错误码 | 每个转换与每条拒绝路径有聚焦用例；`assertNever` 保证穷尽 |
| 契约 | contract 命令/事件/版本协商 | 跨包兼容窗口，含旧版本 host 连新 relay |
| 集成 | 单 relay + 多 host 真实流程 | P0 两实例、P1 起三实例；用真实数据库 |
| 恢复 | 崩溃、重启、回滚、分叉 | ACK 前崩溃、relay 重启、水位对账、`sync_diverged` |
| 安全 | 越权、注入、隔离、供应链 | **安全回归用例库是交付物**，长期保留 |
